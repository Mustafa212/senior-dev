# senior-dev

A Claude Code plugin that runs a coding task the way a senior developer would:

```
align on acceptance criteria → you approve the plan → implement → show
   → a blind reviewer and a blind tester check the work against the user story
   → triage → loop until every criterion is proven (at most 3 rounds)
```

The reviewer and the tester are separate agents that never see the implementer's reasoning, so they
can't inherit its blind spots. "Done" needs evidence (a build, a test run, a test seen failing
without its fix), never a claim.

`skills/senior-dev/SKILL.md` is written for Claude. This file is for you.

## Install

```bash
claude plugin marketplace add Mustafa212/senior-dev
claude plugin install senior-dev@senior-dev
```

On Claude Code 2.1.275 or later, one step also works: `/plugin install senior-dev --marketplace Mustafa212/senior-dev`.

Then, in a new session: `/senior-dev <task, story text, or work-item link>`. If another command
already uses that name, type `/senior-dev:senior-dev`. Claude also starts it on its own when you ask
for work "in phases", "as a senior", or for a review of your branch against a story.

## What you get

| Part | What it does |
|---|---|
| `skills/senior-dev` | The workflow: phases, gates, modes, the state file, triage, the final report |
| `agents/reviewer.md` | The blind reviewer. It has read and search tools only, reads the whole change from one frozen diff, and judges against the story |
| `agents/tester.md` | The blind QA engineer. It designs cases from the story first, then runs them and classifies every failure |

**At the end,** after you've reviewed the work, senior-dev asks one question: commit, push and
open a pull request to the branch the work started from (GitHub or Azure Repos), and link it to the
work item. Nothing happens without your yes.

**One heavy command at a time.** Builds and test suites go through `scripts/heavy.sh`, a
machine-wide lock, so several sessions running in parallel don't stall each other.

Neither agent loads your CLAUDE.md files, so your personal working instructions don't reach them.

## Modes

- **Full** (default): every phase runs.
- **Lite:** a trivial change gets one blind review and no tester. Its evidence is marked
  self-verified.
- **Review existing:** "review my branch against this story" checks code you already wrote.

## Coding rules come from your project

senior-dev ships no coding rules. It applies the project's own rules, in this order:

1. An `AGENTS.md` generated by [ai-standards](https://github.com/Mustafa212/ai-standards), the
   companion plugin that writes the rules into every project and enforces them with linters, hooks
   and CI. Its rule IDs are cited in reviews, and its check command is part of the gate.
2. A project registered in your ai-standards private copy but not adopted: the base, stack,
   architecture, org and project rules from that copy, with the project's exceptions applied (the
   reviewer is told about them, so they aren't reported), plus the latest audit report.
3. Other written rules: `CODING_RULES.md`, rules in `AGENTS.md` or `CLAUDE.md`, and lint or analyzer
   configs.
4. Otherwise, the conventions the codebase already follows consistently.

## Your data stays local

Everything specific to your projects, company or machine is created by the skill **locally**, and
never goes into the plugin:

```
~/.claude/senior-dev/
  config.md                      your tools: work-item / DB MCPs and their quirks, work-log spec, OS quirks
  projects/<project>/notes.md    what runs learned about a project: commands, test setup, traps, branch naming
```

Each run keeps its state in the repo under `.ai-session/` (make sure it's git-ignored), so another
session, or another AI tool, can resume it from the `NEXT` line.

**Optional extras.** The skill works without them and skips whatever is missing.
- A work-item MCP (for example `@azure-devops/mcp`) to fetch stories from links. senior-dev reads
  it, and writes only in the PR step after your yes (the link and the state). In `settings.json`,
  set the tools that step uses to **ask** and deny the other write tools. For `@azure-devops/mcp`:
  ask `wit_work_item_write`, `wit_work_item_link_write`, `repo_pull_request_write`; deny
  `wit_work_item_comment_write`, `repo_pull_request_thread_write`, `repo_create_branch`,
  `work_iteration_write`, `work_capacity_write`. Permission rules are the real barrier: they apply
  to the reviewer and tester agents too, and story text is treated as data, never as instructions.
- A work-log spec at `~/.claude/work-log.md`, for logs somewhere other than `.ai-session/logs/`.
- A second reviewer from another model family (for example the Codex CLI), for security, money or
  data-integrity changes. It runs only when you approve it in the plan, which says what it sends to
  that vendor.
- Standing permission, in `~/.claude/CLAUDE.md`, for Claude to improve the skill in your clone of
  this repo. Without it, Claude proposes each change and waits for your approval.

## Improving it

The skill runs a short retro at the end of every run and proposes improvements. To change the
plugin:

1. Fork or clone this repo, and register your clone as a local marketplace:
   `claude plugin marketplace add <path to your clone>`. Edits apply in place at the next session.
2. Make the change on a branch, with a dated entry in `CHANGELOG.md` that says what changed and
   why, without project names or ticket numbers.
3. Open a pull request. Changes reach everyone through `main`, never by a direct push.

**Releases.** Bump `version` in `.claude-plugin/plugin.json`, head the `CHANGELOG.md` entry with
that version, merge, and push a `vX.Y.Z` tag. The release workflow checks the tag against
`plugin.json` and publishes a GitHub release with that changelog section. Installed copies pick up
the new version with `claude plugin marketplace update senior-dev`, then
`claude plugin update senior-dev@senior-dev`.

## Layout

```
.claude-plugin/plugin.json          plugin manifest (version)
.claude-plugin/marketplace.json     this repo is its own marketplace
skills/senior-dev/SKILL.md          the map: principles, modes, phases, gates, red flags
skills/senior-dev/references/       details read only in the phase that needs them, plus the agent briefs
agents/reviewer.md, agents/tester.md   the blind agents
CHANGELOG.md                        every change, with the reason
.github/workflows/release.yml       a vX.Y.Z tag publishes a GitHub release
```
